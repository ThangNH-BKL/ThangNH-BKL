# Security, consistency and release limitations

This is a single-job, per-user tray application. It never writes the production source and never STORs a final filename. No database or database driver is linked. Credentials are Windows Generic Credentials scoped to the current user; Remember is opt-in. They are not INI values. libcurl debug tracing is disabled, application errors are fixed diagnostic messages, URLs with userinfo are rejected, and logs never include payloads or passwords. Memory clearing is best effort; temporary library/UI string copies cannot be guaranteed erased.

TLS is mandatory for explicit/implicit FTPS, with peer/hostname checks and minimum TLS 1.2. Schannel uses Windows trust. There is no insecure override. SFTP is unsupported. Plain FTP is exposed only with explicit consent and is unencrypted. No analytics, proxy auto-discovery or telemetry is used by the application.

The immutable snapshot is copied with READ/WRITE/DELETE sharing, with size/mtime/identity checks and a second source hash. Continuous writers are deferred. This cannot prove a transactionally coherent snapshot against a producer deliberately rewriting and restoring bytes/metadata during reads. Producer-closed files or a producer-supported filesystem snapshot are needed for that guarantee. Exclusive source locks are respected. No VSS/admin privileges are used.

Every cycle deliberately hashes snapshots and reads back remote content to prove ownership. **Unchanged files are not uploaded, but they do incur RETR traffic.** The requested no-data-transfer cheap unchanged verification is not implemented because this adapter does not use server HASH extensions or trust SIZE/mtime as content proof. It favors correctness over that efficiency requirement. Size mode is lower assurance for the staged object only; final confirmation still uses read-back SHA-256. The extra full remote download requires local disk space as well as bandwidth.

Default Station ID is generated from computer name plus a random suffix; Save persists it. Each PC must have an exclusive server-enforced namespace. Users can edit it; unique names do not themselves enforce ownership. Deliberately sharing a filename across computers is unsupported; the GUI requires exclusive-owner acknowledgment when station separation is disabled. Equal-content adoption is not a distributed ownership grant. FTP has no general CAS; a competing writer can race between hash/stat and RNTO. Use separate accounts/directories and never authorize two writers to the same target.

This implementation always uses a two-step replacement with a temporary missing-final gap; it does not detect or claim atomic replacement. Accepting the gap is an explicit setting. A server/downstream pipeline requiring uninterrupted final visibility is incompatible and replacement stops safely. A failed STOR leaves final intact. A failure after old->rollback may leave final absent until journal recovery restores the verified old copy. On ambiguous failure, good copies remain untouched and future publishing is blocked. The app never falls back to direct overwriting final. Unknown or partial remote objects require manual review.

Local flush + checked same-volume MoveFileEx WRITE_THROUGH + a previous recovery copy are used. These depend on NTFS/storage hardware honoring flushes and rename behavior. No file-backed scheme can guarantee durability across hardware failure. An exclusive open lock file prevents competing local state writers. Within the app, one worker owns state/journal and a run mutex rejects overlap. The `Store` class is worker-owned, not a general concurrent database API.

Resource bounds are conservative: state/journal 64 MiB, 100,000 checkpoints, listings 4 MiB, streaming buffers 64 KiB. State entries are never automatically pruned and the journal is not compacted automatically; reaching a bound stops safely and requires supervised archival. Orphan local spool files and partial remote uploads are preserved after ambiguous crashes. No multi-job GUI, background service, remote HASH support, zero-gap publishing, silent conflict auto-resolution or automatic remote orphan sweeping is provided.

MFC cannot be built or run in the supplied environment. The actual GUI, tray, startup entry, DPI/small-screen layout, MFC runtime ZIP and production server remain **pending release gates**. The GUI uses a status/history table rather than a full job browser, standard message-box validation rather than per-field error decorations, and a next-run UTC timestamp rather than a live countdown. Real screenshots cannot be truthfully supplied before running the MFC build. The included checklist requires them. Suspend/resume logic is tested at scheduler level, not with physical PC power events. Large-file hashing and metadata storage are tested separately from multi-GB FTP upload.

Dependencies are pinned to an auditable source archive, but security advisories and licenses must be re-reviewed before distribution. A successful build is not a production safety certification. See TEST_REPORT.md for the exact executed and unexecuted acceptance cases.
